做一个让用户编辑内容并打印的功能，最后往往会得到三份自称是同一份的文档：编辑器渲染内容，预览克隆一份，打印路径又在别处重建一份。于是预览显示 12 页，PDF 却有 13 页，没有人能说清哪个才是对的——因为从来没有人规定过以哪一份为准。

Imposia 消除的正是这个问题。它把你现有的 HTML 和 CSS 在浏览器内排成一份分页文档，而每个输出面——预览、原生打印、**另存为 PDF**——观察的都是这同一份已完成的文档。

## 你的 HTML 会经历什么

1. 应用把 HTML、CSS 和页面选项交给 Imposia。
2. Core 在临时 iframe 中对下一份文档分页。
3. 分页完成后，Imposia 一步替换可见文档。

如果分页失败，或更新的任务先一步到来，读者看到的仍是上一次完成的文档。他们绝不会看到排到一半的布局。

## 一次提交的源内容能产出什么

| 输出 | 获取方式 | 你得到的结果 |
| --- | --- | --- |
| 预览 | React Viewer | 已完成的页面，直接由 canonical iframe 展示 |
| 打印或 PDF | `print()` | 浏览器原生打印对话框，读者在其中选择打印机或**另存为 PDF** |
| EPUB | `exportEpub()` | 可选。由已提交的源内容生成的可重排 EPUB 3.3 `Blob` |

## 体积与速度

| 项目 | 结果 |
| --- | ---: |
| Core 分页（`mountPageDocument`），minify 并 gzip 后 | 56.7 KiB |
| 包含 Core 的 React 页面查看器（`ImposiaPageViewer`），minify 并 gzip 后 | 67.2 KiB |
| 为 99 页的文章分页 | 125 ms |
| 修改该文章中的一个词并重新提交 | 121 ms |
| 提交后的第一帧渲染 | 1.9 ms |
| 为每个条目都有自己 `<style>` 的 100 条目 Publication 分页 | 94 ms |

2026 年 9 月 23 日在 Apple M4 上的 Chromium 149 中测得。时间为 7 次运行的中位数，体积不含 React 和 React DOM。如需在自己的机器上测量，请在仓库中先运行 `pnpm build`，再运行 `pnpm benchmark`。

## 认清边界

<Callout type="warn" title="Imposia 不生成 PDF 字节">
`print()` 打开的是浏览器自身的打印流程。Imposia 没有 PDF 渲染器，没有 Node 或 CLI 渲染器，也没有服务端出版 API。如果你的应用需要在服务器上得到 PDF 字节，Imposia 不是合适的工具——请改用无头浏览器或服务端渲染器。
</Callout>

Imposia 在浏览器中运行，并以 ESM 形式发布。如果这符合你的应用，请继续阅读[构建第一个页面](/zh-CN/docs/getting-started)。
