画像や表が多い文書、ページ数の多い文書は、ページ分割に時間がかかります。Imposia は次の文書を準備している間も直前に完成した文書を表示し続けます。計算途中のレイアウトが画面に現れることはありません。

## 読者に表示される文書

Core は、表示と印刷の基準となる 1 つの canonical iframe を維持します。canonical iframe には、直近でページ分割に成功した文書が入っています。

React コンポーネントと Viewer は、この iframe を直接表示します。ページを複製したり、2つ目の表示文書を作ったりしません。

## ソース更新時の処理

1. Core が新しいソース用に準備用の iframe（staging iframe）を作成します。
2. 許可されたアセットを読み込み、文書全体を staging iframe でページ分割します。
3. ページ分割に成功すると、Core が canonical iframe の内容を一度に置き換えます。
4. 処理が失敗またはキャンセルされた場合や、さらに新しい処理に置き換えられた場合は、staging iframe を削除し、以前の文書を表示し続けます。

staging iframe をプレビュー、表示、印刷に使うことはありません。

## 出力ごとの生成方法

| 出力 | ソース | 結果 |
| --- | --- | --- |
| プレビュー | Canonical iframe | Viewer が表示する、ページ分割済みの完成ページ |
| 印刷 | canonical ページをトップレベル文書の隔離されたスナップショットに複製してから `Window.print()` を呼び出す | ブラウザー標準の印刷処理。Imposia は PDF バイトを返しません |
| EPUB | 最後に確定した文書のソース | ソースの意味構造から作るリフロー型 EPUB 3.3 `Blob`。ページ DOM の固定レイアウトコピーではありません |

`PageDocument.exportEpub()` は拡張機能を再実行せず、固定されたページレイアウトも直列化しません。

## Viewer とネイティブ印刷が一致する理由

まず Viewer で現在確定している文書の 2、3 ページ目を確認します。次にブラウザーの印刷プレビューで「PDF に保存」を選ぶと、同じ内容とページ順が表示されます。

![Imposia Viewerに表示された同じ2ページ目](/images/publishing-contract/committed-page-viewer.png)

*Viewer の2ページ目には、表の01–22行、繰り返し表ヘッダー、`LEFT / 2` のページ装飾が表示されます。*

![Imposia Viewerに表示された次の表ページとページ装飾](/images/publishing-contract/committed-page-continuation.png)

*Viewer の3ページ目には、続きの23–36行と `RIGHT / 3` のページ装飾が表示されます。*

![PDFに保存を選んだブラウザー印刷プレビューの同じ文書](/images/publishing-contract/native-print-save-pdf.png)

*PDF保存用プレビューにも、上で確認した2、3ページ目と同じ表の内容、ページ順、繰り返し表ヘッダー、ページ装飾が表示されます。*

Imposia は印刷のためにレイアウトを再計算したり、別の PDF レンダラーを作成したりしません。`print()` は確定した canonical ページと生成済み CSS をトップレベル文書の一時的に隔離された Shadow Root へ複製してから、トップレベルの `Window.print()` を呼び出します。この方法により Chromium で iframe の印刷結果が空白になる問題を避けながら、対応範囲内の用紙方向、margin box、繰り返し表ヘッダー、ページ番号、本文の順序を Viewer とブラウザー印刷または PDF 保存結果で一致させます。

印刷用のホストはページ内容と世代ごとの CSS を隔離しますが、CSS の `@page` 規則は文書全体に適用されます。ホストアプリケーションに名前のないグローバルな `@page` 規則があると、Imposia がトップレベル文書へ移した印刷用のページ規則と競合することがあります。印刷中は、競合するグローバル規則を使わないでください。

Viewer と PDF 保存用プレビューの内容が一致するのは、どちらも同じ確定済み文書を使うためです。Imposia が PDF バイトを直接生成するわけではありません。プリンタードライバーの余白、拡大縮小、色補正、ブラウザーごとのフォント計測は最終結果に影響する場合があります。

## 外部リソースを制御する

外部リソースを取得できる経路は、ホストアプリの `assetResolver` だけです。Core はこの経路で作られた Blob URL を管理し、文書を置き換えたときや処理が失敗したとき、コントローラーを破棄したときに URL を解放します。

サニタイズ済みの入力、`assetResolver` の出力、拡張機能には、文書に記載された制限が適用されます。機能を正確に処理できない場合、Imposia は推測で処理せず、コードとメッセージを持つ警告を返します。

## 互換性の境界を確認する

- **安定：** ブラウザー ESM API、iframe のライフサイクル、`assetResolver` によるリソースの隔離、対応するページメディア、ネイティブ印刷、リフロー型 EPUB。
- **制約付き：** 文書に記載された表、flex、grid、段組み、参照、named string。
- **実験的：** 明示的に有効にするページ内脚注とページフロート。これらの機能は警告を返します。
- **未対応：** Node または CLI レンダリング、サーバー書き出し、PDF バイト、固定レイアウト EPUB、任意の CSS フラグメンテーション、ブラウザー間で同一のページ数。

構造的なページ分割の基準には Chromium を使ってください。Firefox と WebKit も公開 API とライフサイクルをサポートしますが、寸法と改行は異なる場合があります。
