Build a feature where people edit content and print it, and you usually end up with three documents claiming to be the same one: the editor renders the content, the preview clones it, and the print path reconstructs it somewhere else. Then the preview says 12 pages and the PDF has 13, and nobody can say which one is correct — because nothing decided which one was authoritative.

Imposia removes that question. It turns the HTML and CSS you already have into one paginated document inside the browser, and every surface — preview, native print, **Save as PDF** — observes that same finished document.

[Why Imposia exists →](/en/docs/concepts/why-imposia)

These guides target **Imposia 0.9.0**. Keep directly installed `@imposia/*` packages on the same version. See the [changelog](/en/docs/changelog), [table guide](/en/docs/guides/tables), and [HTML export guide](/en/docs/guides/html-export) for the recent changes.

## What happens to your HTML

1. Your app passes HTML, CSS, and page options to Imposia.
2. Core paginates the next version in a temporary iframe.
3. When pagination finishes, Imposia replaces the visible document in one step.

If pagination fails or a newer update arrives first, readers keep seeing the last completed document. They never see a half-finished layout.

## What one committed source can produce

| Output | How you get it | What you receive |
| --- | --- | --- |
| Preview | The React Viewer | The completed pages, presented from the canonical iframe |
| Print or PDF | `print()` | The browser's native print dialog, where the reader picks a printer or **Save as PDF** |
| HTML | `exportPageDocumentHtml(committed)` | A standalone string of the committed pages with resolved binary assets inlined; see [HTML export](/en/docs/guides/html-export) |
| EPUB | `exportEpub()` | Optional. A reflowable EPUB 3.3 `Blob` built from the committed semantic source |

## Size and speed

| Consumer route | Gzip size | Gzip budget |
| --- | ---: | ---: |
| Core · PageDocument | 68.6 KiB | 69.5 KiB |
| Core · Publication | 72.9 KiB | 74.0 KiB |
| Viewer · PageDocument | 11.9 KiB | 13.0 KiB |
| Client · PageDocument | 77.4 KiB | 79.0 KiB |
| React · PageViewer | 79.6 KiB | 81.0 KiB |

Bundle sizes are the October 14, 2026 snapshot for **0.9.0**, with React and React DOM excluded. The full Core browser artifact is **75.7 KiB gzip**. Budgets are limits, not measured sizes. [Measurement and budget rationale](https://github.com/EungyuCho/imposia/blob/main/docs/bundle-size.md).

| Measure | Result |
| --- | ---: |
| Paginate a 99-page article | 127 ms |
| Change one word in that article and recommit | 127 ms |
| First rendered frame after a commit | 2.0 ms |
| Paginate a 100-entry Publication where every entry has its own `<style>` | 97 ms |

Timing results remain the September 24, 2026 baseline: Chromium 149 on Apple M4, medians of seven runs. Run `pnpm build`, then `pnpm bundle:size` for sizes or `pnpm benchmark` for timings.

## Know the boundary

<Callout type="warn" title="Imposia does not produce PDF bytes">
`print()` opens the browser's own print flow. There is no PDF renderer, no Node or CLI renderer, and no server publishing API. If your application needs PDF bytes on a server, Imposia is not the right tool — use a headless browser or a server-side renderer instead.
</Callout>

Imposia runs in the browser and ships as ESM. If that matches your application, continue with [Build your first page](/en/docs/getting-started).
