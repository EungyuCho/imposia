title: 미리보기와 출력이 이어지는 방식
description: 앱에서 본 페이지가 브라우저 인쇄와 PDF 저장에도 그대로 이어지는 원리를 설명합니다.
---

이미지, 표, 페이지가 많은 문서는 페이지를 나누는 데 시간이 걸립니다. Imposia는 다음 문서를 준비하는 동안 마지막으로 완성된 문서를 계속 보여줍니다. 계산이 끝나지 않은 레이아웃은 화면에 나타나지 않습니다.

## 사용자가 보는 문서

Core는 화면 표시와 인쇄의 기준이 되는 iframe 하나를 계속 유지합니다. 이 문서에서는 이를 <strong>기준 iframe(canonical iframe)</strong>이라고 부릅니다. 기준 iframe에는 마지막으로 페이지 만들기를 끝낸 문서가 들어 있습니다.

React 컴포넌트와 Viewer는 이 iframe을 그대로 보여줍니다. 페이지를 복제하거나 화면 표시용 문서를 따로 만들지 않습니다.

## 내용이 바뀔 때 일어나는 일

1. Core가 새 내용을 위한 임시 iframe을 만듭니다.
2. 허용된 에셋을 불러와 모든 페이지를 계산합니다.
3. 성공하면 기준 iframe의 내용을 한 번에 바꿉니다.
4. 실패하거나 취소되거나 더 새로운 요청으로 대체되면 임시 iframe을 없애고 이전 문서를 유지합니다.

임시 iframe은 미리보기, 화면 표시, 인쇄에 사용하지 않습니다.

## 출력마다 사용하는 원본

| 출력 | 사용하는 원본 | 결과 |
| --- | --- | --- |
| 미리보기 | 기준 iframe | Viewer에 보이는 완성된 페이지 |
| 인쇄·PDF 저장 | 기준 페이지를 최상위 문서의 격리된 복사본으로 옮긴 뒤 `Window.print()` 호출 | 브라우저의 기본 인쇄 절차. 인쇄 창에서 **PDF로 저장**을 선택할 수 있으며, Imposia는 PDF 바이트를 반환하지 않습니다. |
| EPUB | 마지막으로 확정한 문서 원본 | 페이지 DOM의 고정 레이아웃 복사본이 아닌 리플로우형 EPUB 3.3 `Blob` |

`PageDocument.exportEpub()`은 확장 기능을 다시 실행하지 않으며, 고정된 페이지 레이아웃도 직렬화하지 않습니다.

## Viewer와 인쇄 결과가 같은 이유

먼저 Viewer에서 현재 확정 세대의 2·3페이지를 확인합니다. 그다음 브라우저 인쇄 미리보기에서 `PDF로 저장`을 선택하면 같은 내용과 페이지 순서가 그대로 나타납니다.

![Imposia Viewer에서 같은 두 번째 페이지를 표시한 화면](/images/publishing-contract/committed-page-viewer.png)

*Viewer의 2페이지에는 표의 01–22행, 반복 표 머리글과 `LEFT / 2` 머리말이 표시됩니다.*

![Imposia Viewer에서 표의 다음 페이지와 머리말을 표시한 화면](/images/publishing-contract/committed-page-continuation.png)

*Viewer의 3페이지에는 이어지는 23–36행과 `RIGHT / 3` 머리말이 표시됩니다.*

![브라우저 인쇄 미리보기에서 같은 문서를 PDF로 저장하는 화면](/images/publishing-contract/native-print-save-pdf.png)

*PDF 저장용 인쇄 미리보기에도 앞에서 본 2·3페이지의 표 내용, 페이지 순서, 반복 표 머리글과 머리말이 그대로 나타납니다.*

Imposia는 인쇄를 위해 레이아웃을 다시 계산하거나 PDF 렌더러를 따로 만들지 않습니다. `print()`는 완성된 기준 페이지와 생성 CSS를 최상위 문서의 임시 Shadow Root로 복사하고, 바깥 문서의 `Window.print()`를 호출합니다. 이 방식은 Chromium에서 iframe을 인쇄할 때 빈 페이지가 생기는 문제를 피합니다. 지원 범위 안에서는 용지 방향, 여백 상자(margin box), 반복 표 머리글, 페이지 번호, 본문 순서가 Viewer와 인쇄 또는 PDF 저장 결과에 맞게 유지됩니다.

인쇄 호스트는 페이지 콘텐츠와 세대별 CSS를 격리하지만, CSS `@page` 규칙은 문서 전체에 적용됩니다. 호스트 앱에 이름 없는 전역 `@page` 규칙이 있으면 Imposia가 최상위 문서로 옮긴 인쇄 규칙과 충돌할 수 있습니다. 인쇄 중에는 서로 경쟁하는 전역 규칙을 사용하지 마세요.

Viewer 화면과 PDF 저장용 인쇄 미리보기의 내용이 같은 이유는 둘 다 마지막으로 완성된 문서를 사용하기 때문입니다. Imposia가 PDF 바이트를 직접 만든다는 뜻은 아닙니다. 프린터 드라이버의 여백, 배율, 색상 보정과 브라우저별 글꼴 측정은 최종 결과에 영향을 줄 수 있습니다.

## 외부 리소스를 불러오는 경로

외부 리소스는 앱이 제공한 `assetResolver`를 통해서만 들어옵니다. Core는 이 과정에서 만든 Blob URL을 관리하고, 문서를 교체하거나 작업이 실패하거나 인스턴스를 제거할 때 URL을 폐기합니다.

정제된 입력, `assetResolver` 결과, 확장 기능에는 문서에 적힌 제한이 적용됩니다. 기능을 정확히 처리할 수 없으면 임의로 추측하지 않고 코드와 메시지가 있는 경고를 남깁니다.

## 지원 범위를 확인하세요

- **안정적으로 지원:** 브라우저 ESM API, iframe 수명 주기, 리소스 격리, 지원되는 페이지 미디어, 브라우저 인쇄, 리플로우형 EPUB.
- **정해진 범위에서 지원:** 문서에 적힌 표, flex, grid, 다단, 참조, named string.
- **실험적으로 지원:** 직접 켜야 하는 페이지 내부 각주와 페이지 float. 이 기능은 경고를 남깁니다.
- **지원하지 않음:** Node·CLI 렌더링, 서버 내보내기, PDF 바이트, 고정 레이아웃 EPUB, 임의의 CSS 분할, 브라우저마다 같은 페이지 수를 보장하는 기능.

페이지 구조를 확인할 때는 Chromium을 기준으로 사용하세요. Firefox와 WebKit에서도 공개 API와 문서를 만들고 교체하는 흐름은 동작하지만, 측정값과 줄바꿈은 달라질 수 있습니다.
