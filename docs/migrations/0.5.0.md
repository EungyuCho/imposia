# Migrating from 0.4.1 to 0.5.0

`0.5.0` is a minor release with one breaking change: Core parses the string
domain with the browser's native parser instead of `parse5` (ASA-404,
[ADR 0013](../architecture/0013-browser-native-parsing.md)). Most applications
upgrade without a code change. This note exists so the exceptions are findable
without reading commit history.

```bash
pnpm add @imposia/core@0.5.0 @imposia/viewer@0.5.0 @imposia/client@0.5.0 @imposia/react@0.5.0
```

All four packages move together. Mixing a `0.5.0` package with a `0.4.1` one is
not a supported combination.

## Upgrade for the security patch

`0.5.0` bundles `postcss` 8.5.26 and its transitive `nanoid` 3.3.18. Both were
flagged by `pnpm audit --prod`, and both are bundled *into* the
`@imposia/core` browser artifact rather than staying in the toolchain — so a
consumer on `0.4.1` ships the vulnerable versions to their users and cannot fix
that by overriding a dependency in their own lockfile. Upgrading to `0.5.0` is
the delivered path to the patch.

**Backport decision (recorded 2026-08-21, ASA-443): no `0.4.2` is planned.**
Both advisories were measured against the published `@imposia/core@0.4.1`
artifact, and neither vulnerable path is reachable in it. The postcss advisory
(GHSA-fxqj-rqcc-2cmp, moderate — arbitrary `.map` file read when `from` is
unset) requires Node's `fs`, which the browser bundle replaces with an empty
stub; a hostile `sourceMappingURL` comment at worst throws inside
`postcss.parse`, which Core's CSS sanitizer already catches and converts to
its blocked-stylesheet recovery. The nanoid advisory (GHSA-2v37-7h3g-55p8,
high — custom generators loop indefinitely at size zero) requires calling a
custom generator; the artifact's only nanoid call is postcss's fixed-size
`nanoid(6)`, and `customAlphabet` is bundled dead code with no call site.
Node-side consumption of Core, where the postcss advisory would be live, is
outside the supported browser-only contract. The decision is revisited if a
future advisory against the bundled dependencies is reachable through
caller-supplied CSS in a browser context (see
[`SECURITY.md`](../../SECURITY.md) and the security-fix policy in
[`api-policy.md`](../api-policy.md)).

## What can change for your application

### 1. Warning order follows recovered document order

Warnings were ordered by source character offset. They are now ordered by
document order after HTML error recovery. The two orders agree except where
error recovery relocates content — foster-parented table content is the common
case — and there the recovered order wins.

If you display `warnings` in order, the display order can differ for malformed
markup. If you assert on warning order in tests, an assertion written against
character offsets may need to be rewritten against document order.

### 2. `PAGE_RULE_UNSUPPORTED.sourceIndex` has different numeric values

`nodeOrder()` is now a strided document-order slot rather than a character
offset, and `PAGE_RULE_UNSUPPORTED.sourceIndex` derives from that ordering key.
Its values change. They remain stable and comparable **within** one generation,
which is all the field ever guaranteed — it is an ordering key, not a byte
offset into your source.

Every other `sourceIndex` in the pipeline was already a plain counter and is
unchanged.

### 3. Malformed markup may parse differently

Error recovery is now the browser's, not `parse5`'s. Well-formed markup is
unaffected. Malformed markup is recovered by whichever engine is running, and
error-recovery parity across Chromium, Firefox, and WebKit is pinned by
`tests/e2e/browser-core-parsing-parity.spec.ts`.

### 4. `prepareDocument` now requires a DOM

`prepareDocument`, `prepareDecoration`, and `prepareExtensionInput` need
`DOMParser` and `<template>`. These happened to run under plain Node before;
they no longer do.

This is not a contract change — browser ESM has always been Imposia's runtime
boundary and every downstream API already required a browser — but it is a
real breakage if you were calling `prepareDocument` in a Node script or in a
test running under a non-DOM environment. Run those tests under a DOM
environment (the repository uses `happy-dom`).

## What does not change

- Sanitization posture. The string-domain pass is defense in depth, not the
  load-bearing barrier: every prepared document is re-sanitized in the staging
  iframe before commit, and `DOMParser` documents have no browsing context, so
  scripts never execute and subresources are never fetched during sanitization.
- The live-DOM inspector path (`pageWarningTargetBounds`, Viewer Inspector),
  which keys off `sourceIdentity` markers rather than parse offsets.
- Every committed-document, Viewer, print, and EPUB contract.

## Bundle effect

`parse5` and `entities` left the Core dependency graph. Core · PageDocument is
60.0 KiB gzip — 43.6 KiB below the pre-ASA-404 route, even though this release
also ships three performance escape hatches beside the fast paths they guard.
Those hatches (`experimental.forceSequentialPlacement`,
`experimental.forceLegacyLineEnds`, `experimental.forceFullConstraintCapture`)
are removed in the next minor and the budgets tighten again — see
[`api-policy.md`](../api-policy.md) and [`bundle-size.md`](../bundle-size.md).
